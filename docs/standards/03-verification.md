# 03 验证与测试

能否放心让智能体长时间自主工作，取决于验证做得好不好。**通过与否由测试运行器、linter 或独立的检查判定，不由智能体自己判断。** 研究也发现，智能体的自我评估有偏差，容易把原地打转当成进展。

## 验证阶梯

从窄到宽，依次执行：

1. **格式化与 lint**：只检查改动的文件，速度最快
2. **类型检查**
3. **相关测试**：只跑和改动最相关的测试
4. **完整测试套件**：套件比较快时每次都跑
5. **构建**
6. **运行时验证**：
   - UI：启动应用，用 Playwright 打开改动的页面，截图，操作一遍改动的交互，再看控制台有没有报错
   - CLI 或服务：用真实的输入跑一次改动的命令，或者请求一次改动的接口

每个项目都应该提供一条**和 CI 一致的完整检查命令**（例如 `npm run check`、`make check`），并写进 `AGENTS.md`。

## 测试原则

- **修 bug 先写复现测试**：先确认测试在修复前失败，再修复，然后确认它通过。
- **测行为，不测实现**：断言可以观察到的结果，不要断言内部调用了哪些函数。
- **测试必须确定**：不依赖真实时间、随机数、网络或执行顺序。需要的话就注入时钟和随机种子。
- **测试和代码放在同一个改动里提交**。

## 禁止事项

下面这些做法，除非用户明确要求，否则一律禁止：

- 为了让检查通过，删除、跳过、削弱测试，或者把测试标记为预期失败
- 放宽 lint、类型检查或覆盖率的配置
- 用 `--no-verify` 跳过 git hooks（护栏会拦截）
- 没跑某项检查，却声称它通过了

如果遇到和本次改动无关的失败，先证明不带你的改动时它也会失败，然后把它报告出来，不要在当前任务里顺手修。

## 验证报告

任务结束时，智能体要给出一份简短的验证报告：

```text
验证
- npm run check: 通过
- npx vitest run src/export: 通过（新增 3 个测试）
- 浏览器验证：导出按钮可用，截图见 artifacts/export.png
- 未验证：Safari 下的下载行为（本地环境没有 Safari）
```

## CI 是最终把关

本地验证是为了快速得到反馈，CI 才是合并前的最终把关。CI 跑的检查必须和 `AGENTS.md` 里的完整检查命令一致。各技术栈的 CI 模板见 `templates/<stack>/.github/workflows/`，通用的格式检查和密钥扫描见 `templates/common/.github/workflows/quality.yml`。
