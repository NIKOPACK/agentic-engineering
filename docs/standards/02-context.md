# 02 上下文工程

智能体的表现主要取决于它能看到什么。比起提示词技巧，更重要的是把项目知识整理成**持久、分层、单一来源**的上下文。

## 三层结构

| 层 | 载体 | 放什么 | 加载时机 |
| --- | --- | --- | --- |
| 常驻层 | `AGENTS.md` | 项目简介、目录结构、命令、全局规则 | 每次会话自动加载 |
| 按需层 | Skills（`.agents/skills/*/SKILL.md`） | 某类任务的完整流程和领域知识 | 智能体判断相关时加载，或手动调用 |
| 运行时层 | MCP 服务器、CLI 工具 | 数据库、工单、设计稿、文档等实时数据 | 需要时调用 |

另有两类辅助载体：**规格与 ADR**（`docs/specs/`、`docs/adr/`）记录“为什么这么做”；**护栏**（hooks）负责执行那些必须百分之百遵守的规则。

## 各工具的加载方式

本仓库让三个工具共用一套文件：

| | Codex | Claude Code | pi |
| --- | --- | --- | --- |
| 项目指令 | `AGENTS.md` | `CLAUDE.md`（内容是 `@AGENTS.md`，即导入 AGENTS.md） | `AGENTS.md`（没有时回退到 `CLAUDE.md`） |
| 项目 skills | `.agents/skills/` | `.claude/skills/`（软链接到 `.agents/skills/`） | `.agents/skills/` |
| 护栏 | `.codex/hooks.json` → `policy.py` | `.claude/settings.json` → `policy.py` | `.pi/extensions/agent-policy.ts` → `policy.py` |
| 调用 skill | `$skill-name` 或 `/skills` | `/skill-name` | `/skill:skill-name` |

## AGENTS.md 写作规范

**要写的：**

- 智能体无法从代码里推断出来的信息：项目用途、模块边界、约定、禁区
- **准确的命令**：安装、格式化、完整检查、单个测试、本地运行。每条都要实际跑过
- 全局规则：不能跳过测试、不能碰密钥、不能直接推 main

**不要写的：**

- 代码本身就能说明的东西，比如逐个文件的说明、API 列表
- 只跟某类任务相关的流程，这些放进 skill
- 还没确认的方案，这些放进规格文档的“待决问题”
- 会过时的信息，比如当前进度、临时 TODO

**保持精简**：AGENTS.md 每次会话都会加载，每一行都会占用上下文。建议控制在 100 行以内。超出时，把专项内容拆成 skill，或者在子目录里放一个子 `AGENTS.md`（Codex 和 pi 会逐级加载）。

## Skill 写作规范

- **一个 skill 只负责一类任务**。`description` 里要写清楚“什么时候用”和“什么时候不用”，智能体靠它判断是否加载。
- `name` 只能用小写字母、数字和连字符，并且要和目录名一致（pi 会校验）。`description` 不超过 1024 个字符。
- 正文写成可执行的步骤，每一步都要有明确的完成条件。
- 长参考资料放在 `references/`，确定性的操作写成 `scripts/` 里的脚本，正文只写指引。
- 修改之后运行 `python3 scripts/validate.py` 校验格式。

## 单一来源原则

- 同一条规则只写在一个地方，其他地方引用它。
- 规则变了，就在原处修改，并删除或标记旧的说法。不要另起一份新版本。
- 代码代表的是“现在的实现”，规格和 ADR 代表的是“应该的行为”。两者不一致时，要明确记录为一个实现差距。
