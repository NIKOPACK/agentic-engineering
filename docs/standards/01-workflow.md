# 01 开发流程

本规范的核心是：**人负责定义“做完”的标准并做最终审核，智能体在测试、规格和护栏组成的约束内完成实现。** 智能体自己说“完成了”不算数，验证结果才算。

## 任务分级

开工前先判断任务属于哪一级，不同级别走不同的流程。

| 级别 | 典型例子 | 流程 |
| --- | --- | --- |
| 小改动 | 改错别字、修复原因明确的单函数 bug、升级依赖 | 实现 → 验证 → 提交 |
| 常规改动 | 在单个模块内新增行为、重构 | 计划 → 实现 → 验证 → 自审 → PR |
| 复杂改动 | 跨模块功能，或者改动 API、数据结构、迁移、用户流程；需求有歧义 | **规格** → 确认 → 计划 → 分步实现与验证 → 自审 → PR |

拿不准级别时，按更高一级处理。

## 标准流程

1. **理解**：先读 `AGENTS.md`、相关代码和测试，以及 `docs/specs/`、`docs/adr/` 里的已有决策，再动手。需求有歧义就问，不要猜。
2. **规格**（复杂改动）：用 `spec-first` skill，基于 `docs/specs/_template.md` 写规格，验收标准必须每一条都能被验证。人确认之后才开始实现。
3. **计划**：把工作拆成可以单独验证的小步骤。工具支持计划模式的（例如 Claude Code 的 plan mode），先在计划模式下和人对齐方案。
4. **实现**：一次只解决一件事。不做顺手重构，不批量改格式，不改任务范围以外的文件。
5. **验证**：用 `verify-change` skill 跑项目真实的检查。详见 [03 验证](03-verification.md)。
6. **自审**：用 `self-review` skill，像审别人的代码一样审自己的 diff。
7. **交付**：用 `ship-change` skill，在功能分支上按 Conventional Commits 提交，按模板开 PR。详见 [04 Git](04-git.md)。
8. **人审**：人看 PR 时重点看风险最高的部分。智能体在交接说明里要指出这一处。

## 完成的定义（Definition of Done）

下面几条全部满足，才算完成：

- [ ] 规格里的每条验收标准都有对应的实现和检查（复杂改动）
- [ ] 格式化、lint、类型检查、测试全部通过，并且是实际跑过的
- [ ] 新行为有测试；修 bug 时附带一个修复前失败、修复后通过的测试
- [ ] UI 改动在浏览器里实际看过（截图或 Playwright）
- [ ] diff 只包含本任务相关的改动，没有密钥和调试代码
- [ ] 命令、行为有变化时，`AGENTS.md`、README、规格已同步更新

## 并行与异步

- **一个任务一个工作区**：并行跑多个智能体时，每个任务用独立的 git worktree、分支或云端会话，避免互相覆盖。
- **任务描述要能独立看懂**：交给后台或云端智能体的任务，要写清楚目标、涉及的文件、验收标准和验证命令。
- **子智能体做查找，主智能体做决策**：大范围搜索、调研、审查可以交给子智能体，让主上下文保持干净。
- **人的时间花在审查上**：并行开得越多，审查的压力越大。同时进行的任务数不要超过你能认真审完的数量。

## 什么时候人必须介入

- 需求有歧义，或者有多个合理的方案
- 涉及数据迁移、删除数据、生产环境、计费或权限
- 护栏拦截了某个操作（见 [05 安全](05-security.md)）：由人判断要不要放行，智能体不要绕过
- 同一个问题修了两次还没好：停下来重新分析，不要再继续试
